clone

A coding agent that runs on one DGX Spark: a model server with as much context as the box can hold, and fable, a terminal agent with tool calling that works the way Claude Code does.

It aims at three things at once. A context window of 500k tokens or more, thinking before the model acts, and tool calls that work. Everything lives in one directory on both machines.

It is not a frontier model. The open models that fit in 122 GiB are slower and less sharp than a hosted one, so most of the work here went into finding out which of them can be trusted with a long prompt.

What is in it

The model server

vLLM in NVIDIA's container on the Spark, with one profile per model: weights, window, parsers and memory share. When the window asked for does not fit in the cache, the launcher takes the largest one that does and says so.

fable

A terminal agent in Python. Shell, file read, write and edit, search, web fetch, a task list and read-only subagents, behind a permission check. Five thinking levels, translated into whatever each model family calls them.

A control page

Served from the Spark with the standard library. What is running, memory, downloads with a finish time, switching model and window, and the commands that connect Claude Code or fable from another machine.

What was measured

A long window is only worth having if the model can still find things in it. The acceptance test fills the prompt with numbered records, thousands of lines like this one:

Record 9337: the access code for locker 9337 is 836244.

It then asks for three of the codes, one near the start, one in the middle and one near the end, and wants them back through a tool call. A size passes when the call is made and all three codes are right. It is a harsh test. It is also what a long window is for.

Every model in the table thinks, calls a tool and finishes the tool loop at the window listed. Recall is where they part ways, and how they fail matters as much as where. The Nemotron models return a code from the wrong part of the prompt. Flash-Next, past the length it was trained for, returns the record next door:

Asked for locker 9337, it answered with the code for locker 9338.

Asked for locker 137, it answered with the code for locker 37, and quoted the line it believed it had read.

The Qwen models are trained to 262,144 tokens, and their cards document a way to stretch that. What the stretch does depends on the model. The dense 27B stayed exact at twice its trained length. Flash-Next, which attends sparsely, loses its place. An older model, Qwen3-Coder-Next, stopped calling tools altogether. So a stretched window has to be tested on the model that will use it.

Where that leaves the three targets: Qwen3.8-27B is the only configuration that has been exact past 500k, and it is slow. Flash-Next is the model that suits the hardware, at 49 tokens a second, and it is exact inside 256k. Nothing tested so far is exact at a million.

What the hardware is good for

The Spark is sold as 128 GB and reports 121.7 GiB of unified memory at 273 GB/s. Two rules follow from those numbers.

Decode speed is roughly bandwidth divided by the bytes of weights read per token. A sparse model with a few billion active parameters runs well however large it is in total. A dense model reads all of itself for every token, which is why a 125B model with 6B active does 49 tokens a second here and a dense 27B does 12.

Context comes out of what the weights leave. The server takes a fixed share of the memory, loads the weights and gives the rest to its cache. A model with 93 GiB of weights has room for a few hundred thousand tokens whatever window it was trained for, and a model trained for a million tokens can still be a poor reader of them.

Long prompts also cost time. Flash-Next reads about 2,500 tokens a second, so half a million tokens take under four minutes the first time. The dense 27B needs 22 minutes for the same prompt. The server caches what it has read, and a request that extends the previous one only pays for the new part.

Run it

You need a DGX Spark you can reach over SSH and a machine to work from. Nothing needs sudo, and nothing is installed outside the project directory.

# on your own machine
make config          # config/spark.env with a fresh API key
make deploy          # copy the tree to the Spark

# on the Spark, in the tree
spark/bootstrap.sh   # tools, container image, weights, services, tool-call check

# back on your own machine
make panel           # the control page
make doctor          # context window, speed, thinking and tool calls
make agent           # fable in the current directory

The control page prints one command for Claude Code and one for fable, each ready to paste on any machine that can reach the Spark. Before trusting a model with a long prompt, run the recall test against it:

python3 scripts/context-test.py --base-url http://127.0.0.1:8080/v1 --api-key KEY --sizes 100,250,500
